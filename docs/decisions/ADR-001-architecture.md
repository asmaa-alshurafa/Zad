# ADR-001 — Initial Architecture Decision

- **Title:** Initial Architecture Decision for Zad (ShareBox)
- **Status:** 
  - الأساس التقني الحالي (Single-Activity + Jetpack Compose + Navigation Compose): **مقبول ومُطبَّق (Accepted & Implemented)**
  - المعمارية ثلاثية الطبقات المقترحة (Presentation / Domain / Data) ودمج Firebase وHilt: **مقترح للمراحل القادمة (Proposed)**
- **Context:**
  مشروع Zad (ShareBox) هو تطبيق مجتمعي لطلاب الجامعات. يتطلب المشروع بنية برمجية تدعم البداية السريعة والواضحة مع فريق صغير، وتسمح بالتوسع التدريجي شاشة بشاشة وميزة بميزة دون تعقيد غير مبرر، وتفصل بين العرض وتفاصيل التخزين في حال تمت إضافة مصادر بيانات خارجية لاحقاً.

- **Decision:**
  1. **المرحلة الحالية (Milestone 0 - المُطبَّق):**
     - تطبيق مدخل واحد عبر نشاط رئيسي (`MainActivity.kt`).
     - استخدام واجهات Jetpack Compose بالكامل مع سمة Material 3 (`ZadTheme`).
     - إدارة التنقل المركزي عبر مكتبة Navigation Compose (`AppDestination` و `AppNavGraph`).
     - شاشة ترحيبية أساسية مؤقتة (`HomeScreen`) للتحقق من سلامة البناء ودورة حياة واجهة المستخدم.
  2. **المراحل القادمة (المقترح قيد الاعتماد):**
     - اعتماد نمط MVVM ثلاثي الطبقات (Presentation / Domain / Data).
     - إبقاء طبقة النطاق (Domain) مستقلة تماماً عن أي إطار عمل أو مكتبة خارجية (لا Compose ولا Firebase).
     - قصر التعامل مع خدمات Firebase الخارجية داخل طبقة البيانات (Data) فقط وتنفيذ واجهات المستودعات (Repository Interfaces) هناك.
     - عدم إضافة Use Cases إلا عند وجود منطق عمل مركب يبرر وجودها لتفادي التعقيد المبكر.

- **Alternatives Considered:**
  1. **Clean Architecture الكاملة مع Use Case إلزامي لكل عملية:**
     - *سبب الرفض:* يُضيف طبقات وسيطة زائدة وملفات فارغة لعمليات القراءة والكتابة البسيطة، مما يشتت المطورين في المراحل الأولى.
  2. **نمط MVI (Model-View-Intent) الشامل:**
     - *سبب الرفض:* يتطلب تعقيداً عالياً في صياغة الـ Intents وتتبع الحالات، بينما نمط MVVM مع حالات UI غير قابلة للتعديل كافٍ ومثالي.
  3. **الاتصال المباشر بين واجهات Compose و Firebase دون طبقات وسيطة:**
     - *سبب الرفض:* يربط واجهة المستخدم بتفاصيل تقنية سحابية ويمنع كتابة اختبارات محلية مستقلة ويجعل الانتقال لأي مزود آخر مستقبلاً معقداً للغاية.
  4. **تقسيم المشروع لعدة موديولات Gradle (Multi-module Architecture):**
     - *سبب الرفض:* المشروع في بدايته وفريق العمل صغير، وإنشاء موديول منفصل لكل ميزة يُضيف كلفة إدارة إعدادات Gradle دون عائد ملموس حالياً.

- **Consequences:**
  - *الإيجابيات:* وضوح حدود الكود، إبقاء الكود المصدري الحالي في أدنى حد ممكن (Minimal Foundation)، سهولة اختبار منطق العمل مستقبلاً عند كتابته.
  - *السلبيات والمقايضات:* يتطلب مستقبلاً كتابة محولات (Mappers) بين نماذج Firestore ونماذج الـ Domain عند ربط البيانات.

- **Revisit Conditions (شروط إعادة النظر في القرار):**
  يُعاد تقييم هذا القرار المعماري في الحالات التالية:
  1. عند اتخاذ قرار رسمي بشأن مصدر البيانات الفعلي (سواء كان Firebase أو غيره) قبل بدء Milestone 1.
  2. إذا تعقدت قواعد العمل وتطلبت منطقاً مشتركاً بين عدة شاشات، وحينها يُنظر في اعتماد Use Cases محددة.
  3. إذا نما حجم المشروع وفريق العمل بدرجة تجعل تقسيم التطبيق إلى موديولات Gradle متعددة (Multi-module) أمراً موفراً لوقت البناء والتنظيم.
  4. إذا أظهرت متطلبات الأداء حاجة لأطر إدارة حالة بديلة غير MVVM القياسي.
